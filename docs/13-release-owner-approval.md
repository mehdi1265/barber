# ۱۳ — تأییدیه مالک برای Supabase Staging

> **وضعیت این سند: خالی — هیچ تأییدی دریافت نشده است.**
> تا وقتی این سند توسط مالک پروژه پر و امضا نشود، هیچ Migration، هیچ probe نوشتنی،
> هیچ تست دو دستگاهی و هیچ اتصالی به محیط Staging مجاز نیست.
> در این سند هیچ مقدار محرمانه‌ای (رمز، توکن، کلید) نوشته نمی‌شود؛ فقط نام پروژه و ref.

## ۴. جمله تأیید کتبی مالک

مالک باید این جمله را عیناً تکمیل کند (بدون تغییر معنایی):

> «من تأیید می‌کنم پروژه `<staging-project-ref>` یک محیط **Staging/Test مستقل** است،
> هیچ داده واقعی مشتری در آن وجود ندارد، پروژه Production با ref `<production-project-ref>`
> مشخص است، و اجرای مراحل اعتبارسنجی T17 روی پروژه Staging در بازه `<از> تا <تا>`
> با رعایت محدودیت‌های زیر مجاز است. هر عملیات نوشتنی فقط با تأیید صریح
> `--confirm-ref=<staging-project-ref>` انجام می‌شود.»

امضا: `<نام و امضا>` — تاریخ: `<YYYY-MM-DD>`

## ۵. تأیید خالی بودن داده‌های واقعی Staging

- [ ] بازبینی شد که `public.customers`، `visits`، `payments` و bucket `customer-photos` خالی‌اند.
- [ ] تأیید می‌کنم هیچ داده مشتری واقعی، عکس واقعی یا حساب واقعی در این پروژه نیست.
- [ ] تأیید می‌کنم در صورت نیاز، پاک‌سازی کامل پروژه Staging مجاز است.

## ۶. تأیید استفاده از دو حساب آزمایشی

| مورد | مقدار |
|---|---|
| ایمیل حساب A | `<rls-a@example.test>` |
| ایمیل حساب B | `<rls-b@example.test>` |
| روش تأیید ایمیل | Auto Confirm در Dashboard |

- [ ] هر دو حساب فقط برای تست ساخته شده‌اند و به شخص واقعی تعلق ندارند.
- [ ] رمزها فقط در `.env.rls.local` روی دستگاه محلی نگهداری می‌شوند (نه در Git، نه در چت).

## ۷. تأیید اجرای Migrationهای 001 تا 005

- [ ] اجرای `001`، `002`، `003`، `004`، `005` به ترتیب، **دو بار** (اثبات idempotency) مجاز است.
- [ ] تأیید می‌کنم Migrationها فقط افزودنی/تکرارپذیر هستند و هیچ داده‌ای حذف نمی‌کنند.
- [ ] تأیید می‌کنم محدودیت‌های ترکیبی 004 با وضعیت `NOT VALID` باقی می‌مانند تا گزارش ناسازگاری تمیز شود.
- [ ] تأیید می‌کنم `VALIDATE CONSTRAINT` فقط پس از بررسی گزارش ناسازگاری و با تأیید جداگانه انجام می‌شود.

## ۸. تأیید اجرای تست‌های نوشتنی و پاک‌سازی

- [ ] اجرای `npm run rls:check -- --confirm-ref=<staging-project-ref>` مجاز است.
- [ ] تأیید می‌کنم runner در ۱۱ جدول ردیف‌های probe با marker می‌سازد و فقط همان‌ها را حذف می‌کند.
- [ ] تأیید می‌کنم در صورت ابهام در مالکیت یا شکست پاک‌سازی، اجرا متوقف می‌شود و بررسی دستی لازم است.
- [ ] تأیید می‌کنم هیچ DELETE بدون فیلتر `id` + `user_id` مجاز نیست.

## ۹. تأیید تست دو دستگاه

| مورد | مقدار |
|---|---|
| دستگاه/کلاینت A | `<مدل/مرورگر>` |
| دستگاه/کلاینت B | `<مدل/مرورگر>` |
| شبکه | `<Wi-Fi / داده همراه>` |

- [ ] اجرای ۱۰ سناریوی دو دستگاه (ایجاد، حذف، tombstone، offline، retry، conflict، outbox، no resurrection) مجاز است.
- [ ] تأیید می‌کنم این تست‌ها فقط روی Staging و فقط با حساب‌های A/B انجام می‌شوند.

## ۱۰. تأیید نگهداری Secretها فقط در محیط محلی

- [ ] `SUPABASE_ACCESS_TOKEN`، `SUPABASE_DB_PASSWORD`، `DATABASE_URL` و رمز حساب‌ها فقط در `.env.rls.local` یا محیط شل محلی نگهداری می‌شوند.
- [ ] `.env.local` و `.env.rls.local` در Git نیستند (`.env.*.local` gitignored است).
- [ ] هیچ Secret در گزارش، اسکرین‌شات، چت یا CI log قرار نمی‌گیرد.
- [ ] توکن دسترسی پس از پایان تست revoke می‌شود.

## ۱۱. دامنه تأیید (چه چیزی مجاز نیست)

حتی با امضای این سند، موارد زیر **مجاز نیست** مگر با تأیید جداگانه:

- هر عملیاتی روی پروژه Production.
- اجرای Migration روی Hosted بدون پنجره مشخص‌شده در بخش ۰.
- حذف یا بازسازی پروژه Staging بدون هماهنگی.
- استفاده از حساب واقعی کاربران.
- تغییر کد برنامه برای «سبز کردن» تست.
